# Telegram Document Ingestion Service

Сервис принимает через Telegram фото документов от клиентов, группирует их по отправителю и времени, и отдаёт готовые группы во внешний модуль обработки через REST API.

## Почему Telegram, а не MAX

Взял Telegram - на освоение MAX ушло бы больше времени, чем есть на тестовое.  Ниже описал, что изменится, если переносить решение на MAX.

С другой стороны, если смотреть не на тестовое, а на прод - учитывая блокировки Telegram и санкции, MAX может быть более правильным выбором для компании в долгосрочной перспективе.

### Перенос на MAX

_Лир. отcтупление_ - В техзадании указано "двухэтапная модель загрузки файлов (сначала POST /uploads → получение upload URL, затем передача файла через эту ссылку)" - вообще то относится к загрузке файлов в чат пользователю через бот, а не скачивание фото от пользователя 🤔
ну в целом Юлия сказалa, что задание делалось быстро на скорую руку, поэтому я описал в любом случае взаимодействие с MAX 

- Скачивание файла устроена иначе: MAX выдает прямую ссылку на скачивание файла, благодаря чему можно избежать доп. метода, который получает ссылку на скачивание.
- MAX отдает похожий json сообщения, как в телеграме, но поля не идентичные, так что это потребуется править.
- Домен `platform-api2.max.ru` у MAX уже менялся один раз из-за отзыва сертификатов у российских компаний удостоверяющим центром. Поэтому требуется скачивать сертификат с Госуслуг и устанавливать на сервер как доверенный адрес. А именно скопировать файл в /usr/local/share/ca-certificates/ и выполнить update-ca-certificates.
- Остальная логика (группировка, хранение, выдача групп наружу) не завязана на платформу - вся телеграм-специфика лежит в одном модуле (`app/services/storage.py` + `app/api/telegram_webhook.py`), остальной код трогать не придётся.

## Webhook или polling

Взял webhook. При таком объёме (100+ документов в день) разница между ними не в нагрузке - оба спокойно справятся. Webhook требует публичный HTTPS-адрес - у меня уже была настроена связка сервер + Traefik + сертификат, так что это не добавило сложности.

Polling подойдёт, если домена и белого IP ещё нет (совсем ранний MVP) или просто для локальной отладки, так как ngrok и Cloudflare tunnel вроде не работают сейчас в рф.

## Почему для хранения - реляционная БД, и почему Postgres

Данные тут по природе реляционные: одна группа - несколько файлов, обычная связь один-ко-многим. Но БД дает также из коробки уникальность `telegram_update_id`, чтобы не было дублей, и чтобы статус группы менялся атомарно (без гонки, если группу заберут два потребителя одновременно). Это всё даёт реляционная БД из коробки - на ключ-значение пришлось бы писать логику самому.

Конкретно Postgres - ещё и потому, что де-факто стандарт сейчас и там есть `SELECT ... FOR UPDATE SKIP LOCKED`, который блокирует для доступа строку, если её пытаюстся дергать несколько консюмеров.

## Как группируются фото

Группа = один отправитель + окно по времени (`GROUP_TIMEOUT_MINUTES`, по умолчанию 2 минуты).

Новое фото от юзера: если у него уже есть открытая группа моложе таймаута - кладём туда и сбрасываем таймер. Если нет - создаём новую

Отдельная фоновая задача каждые `GROUP_CHECK_INTERVAL_SECONDS` проверяет, какие группы "остыли" (давно не было новых фото), и закрывает их - переводит в статус `ready`.

### Если пользователи шлют фото альбомом

У Телеграм для альбомов есть `media_group_id` - можно было бы закрывать такую группу сразу, не дожидаясь таймаута, и заодно писать юзеру "фото получены". Не реализовал - это не универсальное решение, пользоваьель всё равно может забыть добавить фото и прислать их позже отдельно. Такие случаи нормально решает только OCR

### Почему не объединяю фото от разных отправителей

Можно было бы группировать просто по времени, не глядя на отправителя - "пришло в одно окно, значит один документ". Но при таком объёме и куче активных пользователей это будет постоянно склеивать чужие документы случайным образом, просто по совпадению времени. А расклеить такую ошибку потом нечем

Если наоборот - не склеить документ одного пользователя, присланный по частям двумя людьми - это не страшно, просто останется лишняя группа, которую можно долепить вручную или через OCR. Поэтому группирую только внутри одного отправителя, а вариант с разными людьми - в разделе "дальнейшие шаги"

## Дубли и ошибки

- **Дубль от Telegram** (он может прислать один и тот же апдейт дважды, если сервер не ответил вовремя): на `telegram_update_id` стоит уникальный индекс в БД + `INSERT ... ON CONFLICT DO NOTHING`. Дубль просто не запишется, без ручных проверок и без Redis.
- **Файл не скачался**: скачивание идёт фоном, с 3 попытками и паузой между ними. Запись сразу появляется в БД со статусом `pending`, потом меняется на `ok` или `failed` - не блокирует ни ответ Telegram, ни обработку остальных фото.
- **Осиротевшие фото**: если у группы вообще ничего не скачалось - она всё равно закроется по таймауту, просто с файлами в статусе `failed`. Не теряется молча.

## Как забирает внешний модуль

- `GET /documents/ready` - список готовых групп с файлами и метаданными.
- `POST /documents/{group_id}/ack` - подтверждение, что группа забрана, переводит в `delivered`, чтобы не отдавать ее еще раз.

Выдача через пуллинг, а не через пуш от нас - если бы сервис сам стучался во внешний модуль, пришлось бы следить за его доступностью, это лишняя точка отказа

## Масштабирование

- Сам приём фото - лёгкий, можно просто поднять несколько инстансов сервиса за балансировщиком. Единственное, что нужно вынести отдельно - фоновую задачу закрытия групп, чтобы она не крутилась одновременно в каждом инстансе и не дёргала БД зазря.
- Если понадобится несколько потребителей на выдаче - текущий контракт (`GET /ready` + `ack`) для этого не готов, см. ниже

## Что сознательно не сделано, но можно сделать

- **Несколько потребителей одновременно.** Сейчас если два потребителя одновременно дёрнут `GET /ready`, оба увидят одну и ту же группу и начнут её обрабатывать - `ack` защитит только от двойной записи статуса, но не от того, что работа уже сделана дважды. Решение - заменить `GET /ready` на `POST /claim`, который через `SELECT ... FOR UPDATE SKIP LOCKED` атомарно резервирует группу за одним потребителем: если её уже взяли, вторая транзакция её просто не увидит. Не стал реализовывать - в задании выдача рассчитана на одного потребителя, но если понадобится масштабировать - вот план 👍
- **Группировка фото от разных отправителей на один документ.** Без OCR или сопоставления по номеру/дате документа это не решить надёжно.
- **Команды боту `/done`, `/new`** для явного закрытия группы руками - не стал делать, потому что не решает основную проблему (документ всё равно может собираться из фото разных людей), это была бы только частичная мера.
- Фоновая задача закрытия групп сейчас живёт внутри самого процесса - при нескольких инстансах сервиса её надо вынести в отдельный процесс/шедулер.

## Запуск

Нужен домен, поддомен с A-записью на IP сервера, Traefik сам получит Let's Encrypt сертификат.

```bash
cp .env.example .env
# заполнить BOT_TOKEN, WEBHOOK_URL, DOMAIN, SUBDOMAIN, ACME_EMAIL

docker-compose up --build
```

При старте сервис сам зарегистрирует webhook в Telegram и создаст таблицы в БД. 
Проверка: `GET /health` должен вернуть `{"status": "ok"}`.

## Демо

```bash
pip install httpx
python demo/poll_ready_documents.py
```

Пишем боту несколько фото с одного аккаунта - часть с паузой меньше таймаута (попадут в одну группу), часть с большей (попадут в разные). 
Скрипт покажет, как группы закрываются и заберутся через `/ack`.
