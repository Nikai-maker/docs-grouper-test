# Telegram Document Ingestion Service

Backend-сервис, который принимает через Telegram фото документов от клиентов,
группирует их по отправителю и временному окну, и отдаёт готовые группы
во внешний модуль обработки через REST API.

## Почему Telegram, а не MAX

Выбор сделан в пользу Telegram Bot API по двум причинам:

1. **Срок сдачи** — короткое окно для реализации, README и демо. Осваивать
   незнакомый двухэтапный upload-flow MAX (`POST /uploads` → upload URL →
   передача файла по ссылке) под таймер — риск не успеть, а не вопрос сложности
   самой по себе.
2. **Отсутствие опыта с MAX API** — тестовое задание не место для первого
   знакомства с новым API вслепую.

Сам текст задания также прямо указывает Telegram как более простой вариант
для тестового.

### Что изменится при переносе на MAX

- Вместо одного вызова `getFile` + скачивания по прямой ссылке — двухэтапная
  схема: сначала `POST /uploads` для получения upload URL, затем отдельная
  загрузка файла по этому URL. Это потребует отдельного шага и, вероятно,
  отдельной обработки ошибок на каждом из двух вызовов (что если `POST /uploads`
  прошёл, а сама загрузка — нет).
- Домен API — `platform-api2.max.ru`, актуальность стоит перепроверять
  (в задании отмечено, что домен может меняться).
- Возможны дополнительные требования по сертификации приложения — это внешний
  процесс, не решается на уровне кода.
- Ядро сервиса (группировка, хранение, контракт выдачи наружу) не меняется —
  платформенная специфика инкапсулирована в одном модуле (`app/storage.py` +
  `app/telegram_webhook.py`), остальной код платформо-независим.

## Webhook vs polling

Выбран webhook. При ~100+ документов/день нагрузка тривиальна для обоих
подходов — разница не в производительности, а в задержке и в отсутствии
постоянного опроса впустую. Webhook требует публичного HTTPS-эндпоинта — это
уже решённая задача (VPS + reverse proxy + сертификат), поэтому webhook не
добавляет ощутимой инфраструктурной сложности.

## Логика группировки

Ключ группы — **только `sender_id`** (один отправитель) + временное окно
(`GROUP_TIMEOUT_MINUTES`, по умолчанию 10 минут).

- Новое фото от отправителя: если есть открытая группа этого отправителя
  моложе таймаута — добавляется в неё, таймер сбрасывается; иначе создаётся
  новая группа.
- Фоновая задача каждые `GROUP_CHECK_INTERVAL_SECONDS` проверяет группы без
  новых фото дольше таймаута и переводит их в статус `ready`.

### Почему не объединяем фото от разных отправителей

Технически возможно объединять по чистому совпадению времени, независимо от
отправителя ("прислали в одно окно — значит один документ"), но при объёме
100+ документов/день и десятках параллельно активных пользователей это даёт
системную проблему: разные клиенты случайно присылают фото *разных* документов
с разницей в минуту, и они ошибочно попадают в одну группу. Расклеить такую
ошибку впоследствии нечем — ни OCR, ни ручной труд здесь не помогают
надёжно, если метаданные не сохранены раздельно.

Асимметрия ошибок: ложное объединение чужих документов — дорогая ошибка,
лишняя группа-сирота от того же документа, присланного вторым отправителем —
дешёвая (можно домержить вручную или на этапе OCR). Поэтому группировка
намеренно ограничена одним отправителем, а межпользовательская склейка
вынесена в раздел "Дальнейшие шаги".

## Идемпотентность и обработка ошибок

- **Дубли апдейтов от Telegram** (ретраи при медленном/недоступном ответе
  сервера): уникальный constraint на `telegram_update_id` в таблице
  `document_files` + `INSERT ... ON CONFLICT DO NOTHING`. Гарантия на уровне
  БД, устойчива к параллельным запросам — без in-memory кэша флагов и без
  Redis, которые для этой задачи избыточны.
- **Сеть недоступна / файл не скачался**: скачивание идёт в фоне
  (`BackgroundTasks`) с retry + backoff (3 попытки). Запись сохраняется сразу
  со статусом `pending` → `ok`/`failed`, не блокирует обработку остальных фото
  и не блокирует ответ Telegram.
- **"Осиротевшие" фото**: если скачивание всех файлов группы завершилось с
  `failed`, группа всё равно закрывается по таймауту как `ready` — записи
  со статусом `failed` видны внешнему модулю, а не теряются молча.

## Контракт с внешним модулем обработки

Пуллинг вместо пуша — сервис не должен знать URL и держать доступность
внешнего модуля, это лишняя точка отказа.

- `GET /documents/ready` — список групп в статусе `ready` со всеми файлами и
  метаданными (отправитель, время получения).
- `POST /documents/{group_id}/ack` — подтверждение, что группа забрана.
  Переводит статус в `delivered`, чтобы группа не отдавалась повторно при
  следующем пуллинге.

## Известные ограничения

- Межпользовательская группировка (когда один документ фотографируют и
  присылают разные люди) не реализована — не решается детерминированно без
  анализа содержимого.
- Идемпотентность и группировка работают в рамках одного процесса/инстанса.
  При горизонтальном масштабировании (несколько инстансов сервиса) фоновая
  задача закрытия групп должна быть вынесена в отдельный процесс/шедулер,
  чтобы не запускаться параллельно в каждом инстансе.
- Explicit-протокол закрытия группы командой (`/done`) не реализован
  сознательно: во-первых, реализуем то, что описано в задании; во-вторых,
  раз документ может дособираться из фото разных отправителей, закрытие
  пула одним конкретным пользователем не решает эту проблему полностью —
  это была бы лишь частичная мера, см. пункт выше.

## Дальнейшие шаги (без реализации)

- OCR / распознавание номера документа или даты на фото → сопоставление
  фото друг с другом независимо от отправителя и временного окна — решает
  проблему межпользовательской группировки надёжнее эвристик по времени.
- Обрезка фона и склейка группы в PDF после того, как группа сформирована.
- Explicit-команды боту (`/done`, `/new`) как дополнительный (не основной)
  сигнал для форс-закрытия группы, если пользователь явно закончил
  присылать фото одного документа.

## Запуск

```bash
cp .env.example .env
# заполнить BOT_TOKEN и WEBHOOK_URL (публичный HTTPS-адрес сервера)

docker-compose up --build
```

Сервис поднимется на `:8000`, при старте сам зарегистрирует webhook в
Telegram (`setWebhook`) и создаст таблицы в БД.

Проверка: `GET /health` → `{"status": "ok"}`.

## Демо

```bash
pip install httpx
python demo/poll_ready_documents.py
```

Затем в Telegram написать боту несколько фото с одного аккаунта — часть с
паузой меньше таймаута (попадут в одну группу), часть с большей паузой
(попадут в разные группы). Скрипт покажет, как группы формируются и
закрываются, и автоматически подтвердит их получение через `/ack`.

```

  storage.py               — скачивание файлов с серверов Telegram
  grouping.py                — логика группировки и фоновая задача закрытия
  telegram_webhook.py         — POST /telegram/webhook
  documents_api.py             — GET /documents/ready, POST /documents/{id}/ack
  main.py                       — точка входа, lifespan, роутинг
demo/
  poll_ready_documents.py       — демо-скрипт опроса готовых групп
docker-compose.yml
Dockerfile
requirements.txt
.env.example
```
